## Project Context

This document records the descriptive, observed state of your project: its current architecture, technology stack, domain conventions, and known deviations from the shipped standards. It is distinct from the normative `docs/standards-*.md` files, which describe how the project SHOULD be structured. Where the two disagree, the normative standard prevails.

> **Important**: Passing `--force` during `init` will overwrite this file, discarding any hand-filled content. If you rely on this file, preserve a backup before running `init --force`.

### Architecture

Desktop application ported to a Rust/Iced stack. The privileged context owns operating-system capabilities: filesystem access, network sockets to the Gitea API, and credential storage through the operating system keystore. The unprivileged UI context renders the interface through the Iced application loop and reaches privileged capabilities only through the declared surface. Window lifecycle (creation, focus, geometry, shutdown) is owned by the privileged context per the Desktop Standards process and trust boundary model.

### Stack

Rust desktop application with the toolchain pinned via `rust-toolchain.toml` (stable channel, edition 2024) and `Cargo.lock` committed. Single crate with layout `src/{main,lib,ui,core,platform}`: `main.rs` is the binary edge (argument handling, logging init, `anyhow` error-to-exit conversion), `lib.rs` exposes the public API and carries `#![forbid(unsafe_code)]`, `ui/` holds the Iced 0.14.x view layer, `core/` holds pure application logic (typed `thiserror` errors, geometry persistence), and `platform/` holds the privileged edge (user-data/cache dirs, single-instance lock file, rolling log writer behind a `tracing` subscriber, panic hook). Dependencies: `anyhow`, `dirs`, `iced 0.14`, `serde`/`serde_json`, `thiserror`, `tracing 0.1`. Gitea instance at git.nsoft.com.ar (Gitea 28.3.0, OpenAPI 3.0.3). API requests authenticate with a PAT in the `Authorization: token` header.

### Observability

The application uses the `tracing` facade: `platform::logging::init` installs one process-wide subscriber at the binary edge, and that subscriber renders every event into the rolling log file (`gitea-stopwatch.log` under the user-data directory, rotating on size and day boundaries with bounded retention). The subscriber is implemented in-crate instead of with `tracing-subscriber`, because the available registry serves `tracing` 0.1 only; the required behaviour — level filtering, structured fields, the panic hook and file rotation — is covered by the crate's own subscriber layer. Verbosity is driven by the `GITEA_STOPWATCH_LOG` environment variable (`off`, `error`, `warn`, `info`, `debug`, `trace`); the default is `info`, so a release build never defaults to `trace`.

### Domain Conventions

Issues are identified unequivocally as `owner/repo#N`, satisfying the forge model of one issue per repository. Time entries are associated with issue comments and the sum of time linked to a comment can be queried. API requests authenticate with a PAT in the `Authorization: token` header and are rejected without a valid PAT.

### Known Deviations from Shipped Standards

None intentional at this stage. Tracked in `docs/standards-gaps.md`: Iced core does not expose role, state and descriptive label to screen readers (accessibility gap requiring AccessKit or platform-specific code), and Iced does not produce installable packages or sign binaries (packaging gap requiring external tools such as `cargo-bundle`).

### Verification and Quality Gates

CI pipeline runs on Linux and Windows: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --all-targets`, a coverage stage via `cargo llvm-cov --lcov` that enforces the 90 % line/function gate on the unit-testable scope (the overall project percentage is tracked as a trend until feature work begins), `cargo audit` and `cargo deny check`. `tests/e2e.rs` runs against an isolated user-data directory and cleans up after execution, and one of its tests executes the shipped binary under an available X11/Xvfb display. SonarQube scan produces a quality-gate result. Branch `main` is protected requiring PR and status checks; Dependabot opens updates for Cargo and GitHub Actions; `Swatinem/rust-cache` provides build caching with cancel-in-progress concurrency.

#### End-to-End Execution of the Shipped Binary

`tests/e2e.rs` carries a test that executes the shipped binary instead of the crate surface: it resolves `CARGO_BIN_EXE_gitea-stopwatch` (the executable Cargo builds for the package) and launches it with `GITEA_STOPWATCH_DATA_DIR` and `GITEA_STOPWATCH_CACHE_DIR` pointing at an isolated temporary tree that is removed when the test ends, including on panic.

The Iced shell needs an X11 display, so the test resolves a display harness before launching. When `DISPLAY` is set and reachable it runs the binary directly on that display and can introspect the X server; otherwise, when `xvfb-run` exists, it runs `xvfb-run -a --server-args=-screen 0 1280x1024x24 <binary>` on a private headless server and cannot introspect it, because `xvfb-run` allocates the display number inside its own process; otherwise it prints a skip reason and passes, so a runner with neither stays green. A `DISPLAY` that is set but unreachable (stale session variable) is treated like a missing one.

Clean shutdown cannot be driven by clicking the window button headlessly, so the binary reads `GITEA_STOPWATCH_E2E_AUTO_CLOSE_MS`: when set to a millisecond delay, the running instance closes its own window after that delay through the same path the close button takes (`CloseRequested` → geometry persisted → `window::close`). The harness is inert when the variable is unset, which is every normal run, and a zero or malformed value leaves it inert as well.

What the test proves by execution: the process edge ran (the startup line is in the isolated rolling log), the X server exposed a mapped window titled `gitea-stopwatch` owned by the launched pid (`xwininfo -root -tree` plus the `_NET_WM_PID` check from `xprop`, when those tools exist), the close path ran (the geometry configuration file was written), the process exited `0` on its own, the single-instance lock was released, and the run recorded no panic. What stays deferred and is asserted through the crate surface instead: the rendered theme and the placeholder-navigation text cannot be read back from a headless window, so `e2e_window_title_theme_and_placeholder_navigation_are_configured` asserts the title, the light theme and both navigation lines through the crate's public constants, while the display test proves the window that renders them is mapped. Pixel-level introspection, a window-manager close-button click, Wayland sessions and macOS/Windows runners are not exercised; those runners skip the display test.

#### Coverage Measurement Scope

The 90 % line and function gate applies to the unit-testable pure logic in `src/core/` and `src/platform/` (errors, geometry clamping and persistence, directory resolution, single-instance lock, rolling log writer), which measures 96.51 % lines and 92.92 % functions. `src/ui/window.rs`, the Iced application loop in `src/lib.rs` and the binary edge in `src/main.rs` are excluded from unit coverage because they require a display server; the end-to-end target covers the shell lifecycle instead. The overall project percentage (87.75 % lines, 84.25 % functions) is therefore reported as a trend rather than a hard gate until feature work begins, per design D6. The 90 % threshold itself is never lowered: the display-bound files are removed from the measurement by configuration, and `coverage/lcov.info` carries only `src/core/**` and `src/platform/**` records. `cargo-llvm-cov` 0.9.1 reads no configuration file of its own and accepts the exclusion only through `--ignore-filename-regex`, so the exclusion is injected with `LLVM_COV_FLAGS='-ignore-filename-regex=(^|/)src/((main|lib)\.rs|ui/)'`, which the tool forwards verbatim to `llvm-cov export`. Cargo's `[env]` configuration reaches only build scripts, rustc, `cargo run` and `cargo test` — never an external subcommand — so `.cargo/config.toml` cannot carry the variable and the capture command must export it: `LLVM_COV_FLAGS='-ignore-filename-regex=(^|/)src/((main|lib)\.rs|ui/)' nsoft-specboot collect bootstrap-rust-desktop-shell`. A bare `cargo llvm-cov --lcov` or a bare `collect` invocation measures the whole project and records the trend percentages instead of the gate, which is why the capture command is recorded here and in `coverage-baseline.json` (`measurement_configuration`). The CI `Run coverage` stage enforces that gate with `cargo llvm-cov --lcov --output-path coverage/lcov.info --fail-under-lines 90 --fail-under-functions 90`, so a regression below 90 % fails the job on both operating systems and the `lcov.info` report is uploaded as a workflow artifact. It injects the same exclusion through `LLVM_COV_FLAGS='-ignore-filename-regex=(^|[\\/])src[\\/]((main|lib)\.rs|ui[\\/])'`: the separator-agnostic character classes matter because `llvm-cov` emits backslash-separated paths on Windows, while the excluded set stays exactly `src/main.rs`, `src/lib.rs` and `src/ui/**` and the 90 % threshold is unchanged.

#### SonarQube Quality Gate

The scan reports `SCAN_STATUS: SUCCESS` and `QUALITY_GATE: PASS`. The gate passes because its conditions are evaluated against the configuration held on the SonarQube server, which carries no hard 90 % coverage condition during this bootstrap phase; coverage is tracked as a trend until feature work begins, per design D6. `sonar-project.properties` declares the analysis inputs only (`sonar.sources`, `sonar.tests`, the LCOV report and the Clippy report) and holds no gate threshold, so the recorded gate result shows that the configured conditions were satisfied and is not evidence that coverage met the 90 % target. That target applies to the unit-testable scope above (96.49 % lines, 92.86 % functions); the overall project percentage is reported alongside it as a trend. The reasoning is recorded here and in the `sonarqube_gate_note` field of `coverage-baseline.json`, and is tracked as a gap in `docs/standards-gaps.md`.

#### Evidence Capture

`nsoft-specboot collect` writes `openspec/changes/<change>/logs/evidence.json` (`schemaVersion: 3`) with the app type, stack and mode plus one record per mandatory producer: `unit-tests` (`cargo test`), `coverage` (`cargo llvm-cov --lcov --output-path coverage/lcov.info`) and `e2e` (`cargo test --test e2e`). Each record carries its command, exit code and status, and the coverage record additionally carries the metrics and thresholds of that run. The manifest establishes that the producers ran and passed; it does not by itself establish that the implementation meets the specifications. Implementation correctness is cross-checked through the requirement-to-code mapping of the change specs and through the end-to-end suite in `tests/e2e.rs`, whose 8 tests cover isolated user data with cleanup, window title presence, theme and placeholder-navigation wiring, single-instance lock rejection, focus forwarding, geometry restore and clamp, logging with the panic hook, and an execution of the shipped binary under an X11/Xvfb display (window opened with the application title, closed through the application's own close path, process exited `0`, lock released, geometry persisted). The coverage metrics inside the manifest belong to the capture run it records; the current baseline is the one in `coverage-baseline.json`. Because the capture exports the coverage scope above, the coverage record carries the unit-testable metrics (96.51 % lines, 92.92 % functions, 100 % branches on a branch-free crate) against the 90 % line and function thresholds, so no recorded metric contradicts the threshold it is measured against; `statements` is `null` because the LCOV format carries no statement counter.
